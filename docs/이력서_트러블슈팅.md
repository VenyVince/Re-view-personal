# Re_View

역할 맥락: 팀장 / 백엔드 / 인프라. Java 21, Spring Boot, Security, MyBatis, Oracle, MinIO, Docker.

## R1. 포인트 적립·차감 동시성 (최우선)

**문제**  
같은 사용자에게 주문 차감, 리뷰 적립, 리뷰 삭제 회수가 겹치면 잔액이 중복 계산되거나 음수가 될 수 있었다.

**원인**  
포인트 이력 insert와 총액 update가 분리되어 있었고, 현재 잔액을 잠그지 않은 채 `point = point + amount`에 가까운 갱신을 했다.

**해결**  
- 변경 경로에 `@Transactional`  
- `SELECT ... FOR UPDATE`로 사용자 포인트 행 잠금  
- 잠금 후 잔액 조회 → 계산 → 명시적 update  
- 차감 후 음수면 요청 거부

**결과**  
동일 사용자 포인트 변경이 트랜잭션 안에서 직렬화되고, 잔액 부족 사용을 서버에서 막을 수 있다.

**이력서 초안**

> 주문·리뷰 보상 등 여러 경로에서 포인트를 동시에 갱신할 때 잔액이 어긋날 수 있어, `SELECT FOR UPDATE`와 트랜잭션으로 행을 잠근 뒤 계산하도록 바꿨습니다. 잔액 부족 요청은 서버에서 차단했습니다.

**면접에서 말할 한계**  
부하 테스트 수치가 없으면 TPS/동시사용자 숫자는 대지 말 것. “Lost update를 막기 위해 행 잠금을 썼다”가 정확한 표현이다.

## R2. MinIO Presigned URL 내부 주소 / 브라우저 주소 분리

**문제**  
백엔드·업로드 API는 살아 있는데, 브라우저에서 이미지 업로드/조회가 실패했다.

**원인**  
Docker 안에서 백엔드는 `minio:9000`으로 붙는다. 브라우저는 그 DNS를 모른다. Presigned URL은 서명에 host가 들어가서, 발급 후 문자열만 바꿔도 서명이 깨진다.

**해결**  
- `minio.url`(컨테이너 내부)와 `minio.public-url`(브라우저) 분리  
- 내부용 `MinioClient`와 공개 URL 발급용 클라이언트를 나눔  
- PUT/GET Presigned URL은 공개 endpoint 기준으로 서명  
- `.env.example`에 두 URL의 역할을 적어 환경별로 주입

**결과**  
로컬 / Compose / 배포에서 이미지 주소 계약을 환경 변수로 맞출 수 있다.

**이력서 초안**

> Docker 내부 MinIO 주소로 Presigned URL을 서명하면 브라우저가 객체에 접근하지 못했습니다. 내부 접속용 클라이언트와 공개 URL 발급용 클라이언트를 나눠, 서명 host와 실제 접근 host를 같게 맞췄습니다.

## R3. Security matcher와 실제 API가 어긋남 + 401/403 혼선

**문제**  
장바구니, 주문, 리뷰 쓰기 등 로그인해야 하는 API가 `/api/mypage/**` 밖에 흩어져 있는데, 설정은 관리자/마이페이지만 막고 나머지는 사실상 열려 있었다. 인증 실패와 권한 부족도 둘 다 400에 가까웠다.

**원인**  
기능이 늘면서 컨트롤러 경로와 `SecurityConfig`가 따로 놀았다. 프론트는 Bearer를 붙이고 백엔드는 세션/CSRF 중심이라 정책 자체도 헷갈렸다.

**해결**  
- 컨트롤러와 프론트 호출을 모아 공개 / 로그인 / 관리자로 분류  
- method+path matcher로 쓰기 API를 인증 필요로 제한, `/api/admin/**`는 `ADMIN`  
- 프론트의 불필요한 Bearer 전송 제거 (세션 유지)  
- EntryPoint 401, AccessDenied 403, `ErrorResponseDTO` JSON으로 통일

**결과**  
미로그인 보호 API와 일반 유저의 관리자 API를 상태 코드로 구분할 수 있다.

**이력서 초안**

> 공개 조회와 쓰기 API가 섞여 `permitAll`에 가까운 상태였습니다. 실제 endpoint를 분류해 matcher에 반영하고, 미인증은 401, 권한 부족은 403으로 나눴습니다.

**주의**  
“모든 API를 잠갔다”고 쓰지 말 것. `anyRequest().permitAll()`을 남긴 기록이 있다. 말한 범위는 “개인 쓰기 API와 관리자 API”로 한정.

## R4. 리뷰 수정 시 기존 이미지 삭제

**문제**  
리뷰만 고쳤는데 기존 사진이 사라졌다.

**원인**  
DB에는 object key를 두고, 조회 응답은 Presigned URL이다. 수정 요청에 기존 URL과 새 key가 같이 오면 서버가 URL까지 새 저장값으로 처리했다.

**해결**  
`http`로 시작하는 값은 저장 대상에서 제외. 새 object key가 있을 때만 이미지 매핑을 교체.

**이력서 초안**

> 리뷰 수정 시 조회용 Presigned URL이 저장용 object key처럼 들어가 기존 이미지가 유실됐습니다. 저장 책임(key)과 조회 책임(URL)을 구분해, URL은 무시하고 새 key만 반영하도록 고쳤습니다.

## R5. 헤더 검색에서 리뷰가 이미지 수만큼 중복

**문제**  
검색 카드에 같은 리뷰가 여러 줄로 나왔다.

**원인**  
`review_images`를 그대로 조인하면 이미지가 3장이면 row가 3개다. 목록 카드에는 대표 이미지 1장만 필요하다.

**해결**  
검색 응답은 대표 이미지 1장만 조인/조회하도록 SQL·응답을 단순화.

**이력서 초안**

> 검색 목록이 이미지 조인 때문에 리뷰 단위로 중복됐습니다. 카드용 대표 이미지 1장만 가져오도록 조회를 바꿔 응답 중복을 없앴습니다.

## R6. Docker 이미지에 `.env`가 들어가는 구조

**문제**  
백엔드 이미지 빌드가 `COPY infra/.env`에 의존해, DB/MinIO 비밀이 레이어에 남을 수 있었다.

**원인**  
로컬 편의를 위해 환경 파일을 이미지에 복사했다. 환경이 바뀌면 재빌드가 필요하고, 이미지 유출 시 비밀도 같이 유출된다.

**해결**  
Dockerfile에서 `.env` 복사 제거. `infra/.env.example`만 두고 Compose/`env_file`로 런타임 주입.

**이력서 초안**

> 컨테이너 이미지에 환경 파일이 포함되지 않도록 Dockerfile 복사를 제거하고, 비밀은 런타임 주입으로 분리했습니다.

# Cosider

역할 맥락: NestJS 서버 인증. JWT access, opaque refresh, Redis, Drizzle, Google/GitHub OAuth, argon2.

## C1. Refresh 토큰 탈취·재사용 (최우선)

**문제**  
Access JWT만 쓰면 탈취 시 만료까지 막을 수 없고, refresh를 DB에 그대로 두면 유출 시 재발급이 무한히 가능하다.

**원인**  
Stateless access와 재발급용 refresh의 책임이 섞이기 쉽다. refresh를 재사용해도 이전 토큰을 무효화하지 않으면 탈취자와 정상 사용자가 동시에 세션을 유지한다.

**해결**  
- Access: 짧은 JWT (약 15분), 서명으로 검증  
- Refresh: 예측 불가 랜덤, DB에는 SHA-256 해시만 저장  
- 재발급 시 기존 refresh revoke 후 새로 발급 (rotation)  
- 이미 revoke된 refresh가 다시 오면 해당 사용자 토큰 전부 revoke

**결과**  
유출된 refresh로는 한 번 이상 재발급하기 어렵고, 재사용 흔적이 있으면 전체 로그아웃에 가깝게 끊을 수 있다.

**이력서 초안**

> Access는 짧은 JWT, Refresh는 해시만 DB에 저장하는 opaque 토큰으로 나눴습니다. 재발급마다 기존 토큰을 폐기하고, 폐기된 토큰이 다시 쓰이면 해당 사용자 세션을 전부 무효화했습니다.

## C2. OAuth CSRF state와 가드 싱글톤 레이스

**문제**  
Google/GitHub 로그인에서 state를 가드 인스턴스 필드에 두면, 동시에 두 브라우저가 로그인할 때 state가 섞일 수 있다. state를 느슨히 비교하면 CSRF에 취약하다.

**원인**  
Nest 가드는 기본이 싱글톤이다. 인스턴스 변수에 state를 넣으면 요청 간에 덮어쓴다. 문자열 `===`는 길이 다른 비교에서 타이밍 힌트를 줄 여지도 있다.

**해결**  
- 시작 시 `randomBytes` state를 HttpOnly 쿠키에 저장, 요청 객체에만 실어 Passport options로 전달  
- 콜백에서 쿠키와 query state를 `timingSafeEqual`로 비교 후 쿠키 즉시 삭제  
- 실패는 JSON이 아니라 프론트 `/login?error=...`로 리다이렉트 (브라우저 콜백)

**이력서 초안**

> OAuth state를 가드 필드에 두면 동시 로그인에 state가 오염됩니다. 요청 단위로 쿠키에 넣고 timing-safe 비교한 뒤 일회용으로 지웠습니다. 실패는 API JSON이 아니라 로그인 페이지로 돌려 브라우저 콜백을 맞췄습니다.

## C3. 이메일 가입과 소셜 계정의 충돌

**문제**  
같은 이메일로 로컬 가입과 Google 가입이 따로 생기면 계정이 쪼개지거나, 반대로 아무 확인 없이 묶이면 계정 탈취가 된다.

**원인**  
이메일은 식별자이지만 provider는 여러 개일 수 있다. “이미 있음”을 한 가지 에러로 처리하면 프론트가 연동과 중복 가입을 구분하지 못한다.

**해결**  
로컬 가입 전 provider 목록을 조회. 로컬이 이미 있으면 conflict. 소셜만 있으면 `REQUIRE_SOCIAL_LINKING`과 provider 목록을 내려 프론트가 연동 플로우로 가게 함. 가입 자체는 메일 인증 전 Redis 대기로 두고, 인증 성공 시에만 DB 트랜잭션으로 user + credential insert.

**이력서 초안**

> 동일 이메일의 로컬/소셜 가입이 섞이지 않도록 provider를 먼저 조회했습니다. 소셜만 있는 경우는 에러 코드로 연동을 유도하고, 신규 가입은 메일 인증 후 트랜잭션으로 반영했습니다.

**정직하게 쓸 한계**  
대기 비밀번호를 Redis에 **평문**으로 넣은 코드가 있다. 이력서에 “가입 보안을 완성했다”고 쓰지 말 것. 물어보면 “인증 전 임시 저장이라 지금은 해시 전 평문이고, 해시 저장으로 바꿀 예정”이 맞다.

## C4. 로그인 시 계정 존재 여부 타이밍

**문제**  
없는 이메일은 바로 거절하고, 있는 이메일은 비밀번호 검증·상태 검사까지 가면 응답 시간으로 계정 존재 여부를 짐작할 수 있다.

**원인**  
실패 분기 순서가 비즈니스 메시지 위주로 짜여 있으면, 사용자 enumeration에 유리하다.

**해결**  
argon2 검증을 상태 검사보다 앞에 두고, 없거나 비밀번호가 틀리면 같은 실패로 취급. BAN/INACTIVE 등은 비밀번호가 맞은 뒤에만 구분.

**이력서 초안**

> 로그인 실패를 ‘없는 계정’과 ‘틀린 비밀번호’로 나누지 않고, 비밀번호 검증을 먼저 해 응답 시간으로 계정 존재를 짐작하기 어렵게 했습니다.

이 항목은 C1/C2 다음 예비용이 적합하다. 혼자 본문으로 쓰기엔 임팩트가 작다.

# 복붙용 이력서 블록

프로젝트 소개 아래에 이렇게만 붙여도 된다.

### Re_View (백엔드/인프라)

- 포인트 적립·차감이 주문/리뷰와 겹칠 때 잔액이 어긋날 수 있어, 사용자 포인트 행을 `SELECT FOR UPDATE`로 잠근 뒤 트랜잭션 안에서 계산·갱신하도록 변경
- Docker 내부 MinIO 호스트로 서명한 Presigned URL을 브라우저가 열지 못해, 내부 클라이언트와 공개 URL 발급 클라이언트를 분리
- 컨트롤러 기준으로 공개/인증/관리자 API를 나눠 Security matcher에 반영하고, 미인증 401·권한 부족 403 JSON 응답으로 정리
- 리뷰 수정 요청에 조회용 URL이 저장용 key처럼 들어가 이미지가 사라지던 문제를, URL 무시 + 신규 key만 반영으로 수정

### Cosider (인증)

- Access JWT와 DB에 해시만 저장하는 Refresh를 분리하고, refresh 재사용 시 해당 사용자 토큰을 전부 폐기
- OAuth state를 싱글톤 가드 필드가 아니라 요청/쿠키 단위로 두고 timing-safe 비교, 실패는 프론트 로그인으로 리다이렉트
- 동일 이메일의 로컬·소셜 가입 충돌을 provider 조회로 구분해, 중복 생성 대신 연동 플로우로 연결

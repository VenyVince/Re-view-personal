## 이번 측정으로 넣을 수 있는 문장

`docs/review_resume.md`는 수정하지 않았다. 포인트 숫자는 `measure.md`의 v0.2.0 재측정이고, 추천 숫자는 v0.3.0이다.

### 기존 문장을 이 조건으로 줄일 때

66행과 128행의 포인트 문장, 37행의 포인트 절에 대응한다.

```
●	테스트 시드 사용자 1명, 시작 잔액 10,000에서 적립 100원 10건과 차감 100원 10건을 동시에 실행하고 5번 반복했다. USER_TABLE 잔액과 point_history의 EARN 합 − USE 합은 다섯 번 모두 10,000으로 같았고, 불일치는 0건이었다
```

### 이력서에 새로 넣을 수 있는 문장

베스트 지급은 기존 이력서 문장에 없다. 일반 잔액이 맞은 사실과 베스트 1행을 한 문장으로 합치지 않는다.

```
●	같은 사용자·같은 리뷰에 베스트 포인트 700원 지급 10스레드가 동시에 들어오자, 중복 확인이 행 잠금보다 앞에 있어 EARN이 9행 남았다. 사용자 행을 SELECT … FOR UPDATE한 뒤에 확인하도록 바꾼 재측정에서는 1행만 남았다
```

v0.1.0의 Compose·Actions 대조는 기존 배포 문장을 파일 기준으로 뒷받침한다. 최근 실행이 `cancelled`라서 배포 성공이나 소요 시간을 새 문장으로 넣지 않는다.

### v0.3.0에서 기존 문장을 나눌 때

37행의 `ROW_NUMBER` 절, 39행, 67행, 128행의 추천 문장에 대응한다. 상품 추천과 리뷰 추천을 한 문장으로 합치지 않는다. 상품 쿼리 원문에는 `ROW_NUMBER`가 없고, 실행 계획에 보이는 `ROW_NUMBER`는 `FETCH FIRST 16`이다.

```
●	정답 픽스처 사용자 1(축 D/S/P/W), 상품 20, 리뷰 40에서 리뷰 추천은 16행이었고 상품 ID 중복은 0건이었다. 상품 1의 리뷰 1은 기본 점수 70, 리뷰 2는 기본 점수 60에 is_checked 1.2배를 적용해 72가 되어 그 상품의 대표로 남았다
●	같은 조건의 상품 추천 원문에는 ROW_NUMBER가 없다. 4축 일치 상품 1은 점수 120으로 16행 안에 있고, 2축 일치 상품 2는 점수 60으로 16행 밖에 있다
```

리뷰 2,000건 JDBC, 워밍업 2회 뒤 10회. 상품 추천 평균 2.357ms, 최댓값 2.807ms. 리뷰 추천 평균 11.481ms, 최댓값 13.299ms. 두 실행 계획 모두 대상 테이블은 `TABLE ACCESS FULL`이다. p95와 개선율은 넣지 않는다.

`e7c2fa82`의 상품 추천은 같은 픽스처에서 19행, 평균 3.630ms, 최댓값 4.381ms였다. 현재 상품 추천은 16행이다. 점수식과 행 제한이 달라 이 차이를 개선율로 쓰지 않는다. 그 커밋에는 리뷰 추천 SQL이 없다.

### v0.4.0에서 기존 문장에 조건을 붙일 때

69행의 검색·정렬·필터에 대응한다. 배포 문장과 한 줄로 합치지 않는다. HTTP 브랜드 필터가 동작한다는 문장은 넣지 않는다. 서비스가 브랜드를 `filter_category` 자리에 넘기면 결과가 비었다.

```
●	헤더 상품 검색에서 키워드 측정토너는 상품 1만 반환하고 삭제된 상품 3은 빠졌다. 키워드 측정의 기본 정렬과 latest는 상품 1, 2 순이고, low_price는 상품 2, 1 순이었다. 리뷰 검색 키워드 리뷰검색어는 리뷰 3 한 건이었다
```

2글자 제한은 `HeaderSearchController`에 있다. SQL에 키워드 `측`을 넣으면 상품 1, 2가 반환된다. 리뷰 2,000건, 키워드 `성능`, JDBC 워밍업 2회 뒤 10회에서 상품 검색은 200행, 평균 6.396ms, 최댓값 7.968ms다. 리뷰 검색은 2,000행, 평균 15.181ms, 최댓값 17.447ms다. `2c4f24ab`는 WHERE가 같고 정렬 키만 달라 개선율로 쓰지 않는다.

### v0.5.0에서 새로 넣을 수 있는 문장

로컬 이력서에는 구매자 제한, 주문 스냅샷, 잔액과 분리된 이력 문장이 없다. 아래는 그 판정이 아니라 이번 측정으로 적을 수 있는 문장이다. 거절 세 건을 서로 다른 오류처럼 쓰지 않는다. 재고 예외 한 번으로 모든 주문 경로가 한 트랜잭션이라고 쓰지 않는다.

```
●	주문자가 아닌 사용자, 다른 사람의 주문상품, 이미 리뷰가 있는 주문상품은 리뷰 작성에서 같은 메시지 잘못된 접근입니다.로 거절됐다. 본인 주문상품 중 리뷰가 없는 1건은 작성 가능했다
●	상품명을 측정토너에서 변경토너로, 가격을 12,000에서 999로 바꾼 뒤에도 기존 주문상품은 측정토너, 12,000이었다. 그 다음 주문으로 만든 주문상품은 변경토너, 999였다
●	잔액 10,000에서 usePoint 100원 1건 뒤 잔액은 9,900이었고 USE 100원 이력은 1행이었다. 재고 0인 상품에 포인트 50원을 쓰려다 재고 예외가 난 뒤에는 주문 수와 잔액이 예외 전과 같았다
```

### v0.6.0에서 기존 문장에 조건을 붙일 때

65행과 128행의 이미지 문장에 대응한다. 수정 API에는 이미지 제거가 없다. 유지 경로의 응답이 기존 이미지를 다시 서명해 돌려준다고 쓰지 않는다. 만료는 URL의 `X-Amz-Expires`가 코드의 10분·5분과 같은 것이고, 시간이 지난 뒤 거절되는지는 보지 않았다.

```
●	리뷰 1의 이미지 key가 reviews/fixture/review-1.jpg일 때, 수정 요청의 images가 비어 있거나 http URL만 있으면 REVIEW_IMAGES는 그 key 그대로였다. http URL 문자열은 테이블에 남지 않았다
●	본문이 비어 있으면 리뷰 내용이 필수입니다.가 나고 key와 본문은 그대로였다. reviews/로 시작하는 새 key를 넘기면 REVIEW_IMAGES는 그 key 한 줄로 바뀌었다
●	리뷰 업로드 발급 응답은 objectKey와 presignedUrl뿐이고 파일 바이트는 없었다. 그 URL에 13바이트를 PUT하면 상태 200이고, DB에는 URL이 아니라 reviews/ key가 남았다. PUT URL의 X-Amz-Expires는 600, 이어서 만든 GET URL은 300이었다
```

●	빈 로그인 JSON은 400 Validation Failed였다. 본문에 id: 아이디를 입력해주세요.와 password: 비밀번호를 입력해주세요.가 있었다

## v0.9.0 판정

`docs/review_resume.md`는 수정하지 않았다. 문장별 이유는 `measure.md`의 v0.9.0이다.

유지하는 현재 파일 사실은 하나다. 루트 Dockerfile에 `.env` COPY가 없고, workflow는 Secrets로 env 파일을 만든다.

수정은 확인한 조건으로 줄을 나누는 일이다. 상품 추천과 리뷰 추천, 일반 잔액과 베스트 지급, 검색과 배포를 한 문장으로 두지 않는다. 위의 초안은 그 수정 문장이다.

추가하지 않는 것은 구매자 제한, 주문 스냅샷, 베스트 9행과 1행, MinIO 파일 1건의 만료 숫자, 선정 쿼리의 리뷰 4건, 보안 다섯 요청이다. 측정은 됐고 로컬 이력서에는 없다.

제외는 운영 cron의 정기 지급, 배포 성공과 소요 시간, 부하 감소, 개선율, API 전체 보호율, 136행의 인가를 맞췄다는 문장이다.

# Re:View 이력서 정량 근거 보완 측정 계획서

## 1. 문서 목적

본 문서는 Re:View 프로젝트의 이력서에 기재된 기술적 경험을 객관적인 테스트 결과로 뒷받침하기 위한 추가 측정 계획을 정의한다.

기존 Phase 1에서 작성한 테스트 코드와 측정 환경을 최대한 재사용하며, 아직 확보되지 않은 측정값을 보완하는 것을 목적으로 한다.

이번 측정의 핵심 목표는 다음과 같다.

1. 일반 포인트 적립·차감의 동시성 정합성 확인
2. 상품 추천 및 리뷰 추천 SQL의 실행 시간 측정
3. 상품 검색 SQL의 실행 시간 측정
4. 추천 SQL의 실행 계획 분석

측정 결과는 이력서의 STAR 중 Result(R)를 작성하는 근거로 활용한다.

- 측정 결과가 확인되지 않은 경우 추정값을 작성하지 않는다.
- 기존 결과와 추가 측정 결과를 구분한다.

- 10회 측정 결과로 p95 등의 백분위 지표를 주장하지 않는다.

## 3. 테스트 1. 일반 포인트 동시성 정합성 측정

### 3.1 테스트 목적

동일 사용자를 대상으로 여러 스레드가 포인트 적립 및 차감 요청을 동시에 실행할 때 최종 포인트 잔액과 포인트 이력 간 정합성이 유지되는지 확인한다.

기존 테스트에서는 100원 적립 10건과 100원 차감 10건을 동시에 실행하도록 구성되어 있다.

이번 측정에서는 기존 테스트의 최종 결과를 명확하게 기록하는 데 집중한다.

### 3.2 테스트 대상

- 일반 포인트 적립 로직
- 일반 포인트 차감 로직
- 사용자 포인트 잔액
- 포인트 이력 테이블(point_history)

### 3.3 테스트 조건

| 항목 | 조건 |
|---|---|
| 사용자 | 측정용 사용자 |
| 초기 잔액 | 기존 테스트 설정값 사용 |
| 적립 요청 | 100원 × 10건 |
| 차감 요청 | 100원 × 10건 |
| 동시 실행 요청 | 총 20건 |
| 실행 방식 | ExecutorService |
| 동시 실행 제어 | CountDownLatch |
| 실행 순서 | Random(20261104) |
| 반복 횟수 | 5회 |
| 측정 대상 | 최종 잔액 및 포인트 이력 |

초기 잔액과 요청 순서는 기존 테스트 설정을 유지한다.

### 3.4 테스트 절차

1. 측정용 사용자의 포인트 잔액을 초기화한다.
2. 해당 사용자의 기존 포인트 이력을 초기화한다.
3. 적립 요청 10건과 차감 요청 10건을 준비한다.
4. ExecutorService를 이용해 20개의 작업을 실행할 준비를 한다.
5. CountDownLatch를 이용해 작업들이 동시에 시작하도록 제어한다.
6. 모든 작업이 종료될 때까지 대기한다.
7. 사용자 테이블에서 최종 포인트 잔액을 조회한다.
8. point_history에서 EARN 및 USE 이력을 조회한다.
9. 적립 합계에서 차감 합계를 계산한다.
10. 최종 잔액과 이력 합계를 비교한다.
11. 위 과정을 총 5회 반복한다.

### 3.5 측정 항목

| 측정 항목 | 기록 내용 |
|---|---|
| 라운드 | 1~5회 |
| 초기 잔액 | 실행 전 포인트 |
| 적립 성공 건수 | 실제 성공한 적립 요청 수 |
| 차감 성공 건수 | 실제 성공한 차감 요청 수 |
| 적립 이력 합계 | EARN 금액 합계 |
| 차감 이력 합계 | USE 금액 합계 |
| 최종 잔액 | 실행 종료 후 사용자 잔액 |
| 예상 잔액 | 초기 잔액 + 적립 - 차감 |
| 이력 기준 잔액 | 초기 잔액 + EARN - USE |
| 잔액 불일치 | 실제 잔액과 이력 기준 잔액의 차이 |
| 예외 발생 건수 | 실행 중 발생한 예외 수 |

### 3.6 결과 판정 기준

다음 조건을 기준으로 결과를 판정한다.

- 모든 요청이 정상 처리되었는지 확인한다.
- 최종 잔액이 예상 잔액과 일치하는지 확인한다.
- 최종 잔액이 포인트 이력 합계와 일치하는지 확인한다.
- 5회 반복 측정에서 동일한 정합성이 유지되는지 확인한다.

단, 차감 요청이 잔액 부족 등의 이유로 실패할 수 있는 구조라면 성공한 요청만 반영하여 예상 잔액을 계산한다.

### 5.8 주의 사항

기존 기능 테스트에서 서비스와 매퍼 간 브랜드 검색 인자 전달 문제가 발견되었다.

- 매퍼에 직접 전달한 조건으로 실행한 SQL 성능
- 실제 서비스 호출을 통해 실행한 검색 결과

매퍼 직접 호출 결과를 실제 서비스 검색 성능이나 정상 동작의 근거로 확대 해석하지 않는다.

## 6. 테스트 4. 추천 SQL 실행 계획 분석

### 6.1 테스트 목적

실행 시간만으로 확인하기 어려운 SQL의 내부 실행 특성을 보완한다.

### 6.2 분석 대상

- findRecommendProducts
- findRecommendReviews

### 6.3 분석 항목

| 항목 | 확인 내용 |
|---|---|
| 테이블 접근 | Full Table Scan 여부 |
| 인덱스 접근 | Index Scan 여부 및 사용 인덱스 |
| 조인 방식 | Nested Loops, Hash Join 등 |
| 정렬 연산 | Sort 및 정렬 관련 연산 |
| 윈도우 함수 | ROW_NUMBER() 처리 구조 |
| 실행 비용 | 실행 계획에 표시된 Cost |
| 주요 병목 | 상대적으로 비용이 높은 연산 |

실제 실행 계획에 나타난 항목만 기록하며, 확인되지 않은 연산은 추정하지 않는다.

### 6.4 분석 절차

1. Oracle XE에 측정용 데이터를 준비한다.
2. 상품 추천 SQL의 실행 계획을 조회한다.
3. 실행 계획의 테이블 접근 방식을 확인한다.
4. 조인 및 정렬 연산을 확인한다.
5. Cost 및 주요 연산을 기록한다.
6. 리뷰 추천 SQL에도 동일한 절차를 적용한다.

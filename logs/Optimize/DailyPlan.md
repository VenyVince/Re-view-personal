# Day1: 측정 기준과 기록 양식 고정

## Todo A: 측정 항목 확정

### Details

- Where: `logs/Optimize/Plan.md`, `logs/Optimize/Mature.md`의 측정 항목을 기준으로 정리한다.
- How: 평균 응답 시간, p95, p99, RPS, DB 실행 시간, 응답 payload 크기, 이미지 URL 생성 호출 수를 기본 항목으로 고정한다.
- Why: API마다 다른 기준으로 측정하면 결과를 비교할 수 없기 때문에, 첫날에 공통 기준을 먼저 고정한다.

## Todo B: API별 결과표 템플릿 작성

### Details

- Where: `logs/Optimize` 아래에 API 측정 결과를 기록할 문서를 만든다.
- How: API명, 요청 조건, 데이터 규모, 이미지 조건, 평균 응답 시간, p95, p99, DB 시간, payload 크기, 특이사항을 같은 순서로 적을 수 있게 만든다.
- Why: 측정 중 기억에 의존하지 않고, 나중에 병목 후보를 영향도 기준으로 비교하기 위해서다.

## Todo C: 데이터 조건 정의

### Details

- Where: 상품, 리뷰, 이미지가 사용되는 API를 기준으로 조건을 나눈다.
- How: 상품 100건, 1,000건, 10,000건을 기본 구간으로 잡고, 리뷰 수와 이미지 수는 API별로 필요한 만큼 추가한다.
- Why: 데이터가 늘어날 때 응답 시간이 선형으로 증가하는지, 특정 구간부터 급격히 느려지는지 확인하기 위해서다.

## Todo D: 이미지 조건 정의

### Details

- Where: 상품 목록, 검색, 리뷰 목록, 상품 상세 리뷰, 추천 API처럼 이미지 URL 변환이 있는 API를 기준으로 본다.
- How: 상품당 이미지 1개, 상품당 이미지 다수, 이미지 대량 누적 상태를 분리한다.
- Why: DB 조회가 빠르더라도 `presignedUrlGet` 반복 호출 때문에 응답 시간이 늘어날 수 있기 때문이다.

## Checklist

- [x] API별 결과표 템플릿이 준비되어 있다. Check: API명, 요청 조건, 데이터 규모, 이미지 조건, 주요 수치, 특이사항을 같은 형식으로 적을 수 있는지 확인한다.
- [x] 데이터 규모 조건이 명확하다. Check: 100건, 1,000건, 10,000건 기준이 문서에 적혀 있는지 확인한다.
- [x] 이미지 조건이 분리되어 있다. Check: 이미지 1개, 이미지 다수, 이미지 대량 누적 상태가 별도 조건으로 적혀 있는지 확인한다.

# Day2: 테스트 데이터 준비

## Todo A: 상품 데이터 규모별 준비

### Details

- Where: 상품 목록 API, 검색 API, 추천 API가 사용하는 상품 테이블과 관련 테이블을 기준으로 준비한다.
- How: 100건, 1,000건, 10,000건 조건을 만들고 각 조건에서 동일한 요청을 반복할 수 있게 상태를 기록한다.
- Why: 같은 API라도 데이터 규모에 따라 병목 위치가 달라질 수 있기 때문이다.

## Todo B: 리뷰와 이미지 데이터 준비

### Details

- Where: 상품 상세 리뷰 API, 리뷰 목록 API, 마이페이지 리뷰 검색 API에서 사용하는 리뷰와 `review_images` 데이터를 기준으로 준비한다.
- How: 리뷰가 적은 상품, 리뷰가 많은 상품, 이미지가 많은 리뷰를 구분해서 테스트할 수 있게 만든다.
- Why: 리뷰 API는 조인 row 증가와 Java 그룹핑, 이미지 URL 변환이 함께 발생하기 때문이다.

## Todo C: 반복 측정 가능한 상태 정리

### Details

- Where: 측정 문서의 데이터 조건 섹션에 기록한다.
- How: 측정에 사용한 상품 ID, 검색 키워드, 사용자 ID, 페이지 번호, 이미지 개수 조건을 적어 둔다.
- Why: 나중에 재측정할 때 같은 조건을 재현하지 못하면 개선 전후 비교가 의미 없어지기 때문이다.

## Checklist

- [ ] 상품 데이터 규모별 조건이 준비되어 있다. Check: 100건, 1,000건, 10,000건 조건에서 사용할 상품 데이터 상태를 설명할 수 있는지 확인한다.
- [ ] 리뷰와 이미지 테스트 조건이 준비되어 있다. Check: 리뷰가 적은 상품, 많은 상품, 이미지가 많은 리뷰를 구분할 수 있는지 확인한다.
- [ ] 반복 측정에 필요한 식별자가 기록되어 있다. Check: 상품 ID, 사용자 ID, 검색 키워드, 페이지 번호 같은 재현 조건이 문서에 적혀 있는지 확인한다.
- [ ] 측정 전 데이터 상태가 고정되어 있다. Check: 측정 중 데이터가 계속 바뀌지 않도록 기준 시점이나 조건을 기록했는지 확인한다.

# Day5: 이미지 경로 점검

## Todo A: 업로드 검증 구조 확인

### Details

- Where: `ImageUploadController`, `ImageService`의 업로드 URL 발급 코드를 확인한다.
- How: 파일 본문 검사, MIME 타입 검증, 파일 크기 제한, 확장자 검증이 있는지 체크리스트로 정리한다.
- Why: 현재 구조가 파일명만 받아 presigned PUT URL을 발급한다면, 성능 문제와 별개로 보안 위험을 분리해서 관리해야 하기 때문이다.

## Todo B: 내부용 URL과 외부용 URL 분리 필요성 판단

### Details

- Where: MinIO 설정, nginx 설정, 이미지 URL 생성 로직을 확인한다.
- How: 서버 내부 통신용 endpoint와 브라우저 접근용 endpoint가 같은지, 운영 환경에서 문제가 될 수 있는지 적는다.
- Why: 개발 환경에서는 동작해도 배포 환경에서 내부 주소가 외부로 노출되거나 접근 불가능한 URL이 내려갈 수 있기 때문이다.

## Todo C: 이미지 URL 반복 생성 병목 정리

### Details

- Where: 상품 목록, 리뷰 목록, 검색 결과, 추천 결과, 장바구니, 위시리스트 등 `presignedUrlGet` 사용 위치를 기준으로 본다.
- How: API별 응답 1회당 URL 생성 호출 수와 중복 key 재생성 가능성을 기록한다.
- Why: 같은 이미지 key가 반복 변환되면 DB보다 애플리케이션 레벨 URL 생성이 더 큰 병목이 될 수 있기 때문이다.

## Checklist

- [ ] 업로드 검증 체크리스트가 작성되어 있다. Check: 파일 본문, MIME 타입, 파일 크기, 확장자 검증 여부가 각각 표시되어 있는지 확인한다.
- [ ] 내부용 URL과 외부용 URL 분리 필요성이 판단되어 있다. Check: 현재 endpoint 구조와 배포 환경에서의 접근 가능성이 문서에 적혀 있는지 확인한다.

- [ ] 이미지 성능 문제와 보안 문제가 분리되어 있다. Check: 병목 후보와 검증 부족 항목이 같은 목록에 섞이지 않고 따로 정리되어 있는지 확인한다.

# Optimization Todo

`Optimize.md`와 `Mature.md`를 바탕으로, 성능 개선 전에 먼저 해야 할 일부터 나중에 해도 되는 일까지 순서대로 정리한다.

## 1. 측정 기준부터 고정

1. 현재 환경에서 응답 시간, p95, p99, RPS, DB 실행 시간, payload 크기를 기록하는 기준을 만든다.
2. 상품 수 100, 1,000, 10,000건 기준의 테스트 데이터를 준비한다.
3. 이미지 수 1개, 다수, 대량 누적 상태를 구분해서 측정 조건을 만든다.
4. 실측 결과를 남길 템플릿을 정리한다.

## 2. 가장 먼저 벤치마크할 API

1. 상품 목록 API를 먼저 측정한다.
2. 통합 검색 API를 다음으로 측정한다.
3. 상품 상세 리뷰 API를 측정한다.
4. 리뷰 목록 API를 측정한다.
5. MinIO 이미지 발급 API를 측정한다.

## 3. 이미지 관련 경로 점검

1. 이미지 업로드 요청이 파일명만 받는 구조인지 다시 확인한다.
2. 파일 본문 검사 부재, MIME 타입 부재, 크기 제한 부재를 실제 위험 항목으로 정리한다.
3. 내부용/외부용 URL 분리 필요 여부를 확인한다.
4. 이미지 URL 생성 호출 수를 API별로 기록한다.
5. 이미지 누적 시 응답 시간과 저장소 부담이 어떻게 변하는지 측정한다.

## 4. 중간 우선순위 API 측정

1. 마이페이지 리뷰 검색 API를 측정한다.
2. 주문 목록 API를 측정한다.
3. 추천 API를 측정한다.
4. 주문 처리 API를 동시 요청 기준으로 측정한다.
5. 포인트 처리 API의 `FOR UPDATE` 대기 시간을 측정한다.

## 5. 배치 작업 측정

1. 월간 베스트 리뷰 갱신 배치의 수행 시간을 측정한다.
2. 후보 리뷰 수가 늘어났을 때 실행 시간이 어떻게 변하는지 확인한다.
3. 배치 중 DB 부하와 트랜잭션 유지 시간을 기록한다.

## 6. 병목 확인 후 개선 후보 정리

1. 조인, 서브쿼리, `LIKE '%...%'`, `OFFSET/FETCH`, `ROW_NUMBER`, `DBMS_RANDOM` 사용 구간을 우선 검토한다.
2. 이미지 URL 변환 반복이 큰 API부터 개선 후보를 추린다.
3. 페이징이 없는 목록 API를 개선 후보로 분리한다.
4. 동시성 경합이 확인되는 주문과 포인트는 별도 후보로 분리한다.

## 7. 나중에 해도 되는 일

1. `ORDER BY DBMS_RANDOM.VALUE` 최적화는 실제 호출 빈도와 데이터 규모를 본 뒤 결정한다.
2. 베스트 리뷰 선정 쿼리 최적화는 배치 시간이 문제될 때 우선 적용한다.
3. MyBatis cache 설정 검증은 측정 결과가 애매할 때만 검토한다.
4. 목록 응답 DTO의 큰 텍스트 컬럼 정리는 응답 크기 개선이 필요할 때 적용한다.

## 8. 안 해도 될 수 있는 일

1. 현재 영향이 확인되지 않은 설정 변경은 보류한다.
2. 실제 병목으로 드러나지 않은 API는 선제적으로 손대지 않는다.
3. 운영 빈도가 낮은 관리자용 랜덤 추천은 수치가 필요할 때만 다룬다.

# Optimization Plan

이 계획은 `Todo.md`의 우선순위를 기준으로 한다. 핵심 원칙은 먼저 측정 기준과 재현 가능한 데이터를 고정하고, 병목으로 확인된 구간만 개선 후보로 올리는 것이다.

## 목표

1. 주요 API와 배치 작업의 현재 성능 기준선을 만든다.
2. 데이터 규모와 이미지 누적 상태에 따른 성능 변화를 기록한다.
3. 추측 기반 최적화를 피하고, 실측 결과로 개선 우선순위를 정한다.
4. 이미지, 페이징, 검색, 동시성, 배치 부하를 분리해서 병목을 판단한다.

## 산출물

1. API별 성능 측정 결과표
2. 테스트 데이터 규모별 비교표
3. 이미지 상태별 응답 시간 및 payload 크기 비교표
4. DB 실행 시간 및 주요 쿼리 병목 목록
5. 개선 후보 우선순위 목록
6. 보류 항목과 보류 사유

## 1단계: 측정 기준 고정

### 작업

1. 측정 항목을 고정한다.
   - 평균 응답 시간
   - p95
   - p99
   - RPS
   - DB 실행 시간
   - 응답 payload 크기
   - 이미지 URL 생성 호출 수
2. 상품 수 기준 테스트 데이터를 준비한다.
   - 100건
   - 1,000건
   - 10,000건
3. 이미지 조건을 분리한다.
   - 상품당 이미지 1개
   - 상품당 이미지 다수
   - 이미지 대량 누적 상태
4. 측정 결과 기록 템플릿을 만든다.

### 종료 조건

1. 모든 측정 항목의 정의가 문서화되어 있다.
2. 동일 조건에서 반복 측정할 수 있는 데이터 상태가 준비되어 있다.
3. API별 결과를 같은 형식으로 비교할 수 있다.

## 2단계: 1차 핵심 API 벤치마크

### 측정 순서

1. 상품 목록 API
2. 통합 검색 API
3. 상품 상세 리뷰 API
4. 리뷰 목록 API
5. MinIO 이미지 발급 API

### 확인할 내용

1. 데이터 증가에 따라 응답 시간이 선형으로 증가하는지 확인한다.
2. payload 크기가 급격히 증가하는 API를 찾는다.
3. DB 실행 시간이 긴 API와 애플리케이션 처리 시간이 긴 API를 구분한다.
4. 이미지 URL 변환 또는 발급 호출이 반복되는 지점을 기록한다.

### 종료 조건

1. 1차 핵심 API별 기준선이 기록되어 있다.
2. API별 병목 유형이 DB, 이미지, payload, 페이징, 애플리케이션 처리 중 하나 이상으로 분류되어 있다.

## 3단계: 이미지 경로 점검

### 작업

1. 이미지 업로드 요청이 파일명만 받는 구조인지 확인한다.
2. 다음 항목을 실제 위험 목록으로 정리한다.
   - 파일 본문 검사 부재
   - MIME 타입 검증 부재
   - 파일 크기 제한 부재
3. 내부용 URL과 외부용 URL 분리 필요 여부를 확인한다.
4. API별 이미지 URL 생성 호출 수를 기록한다.
5. 이미지 누적 상태에 따른 응답 시간과 저장소 부담을 측정한다.

### 종료 조건

1. 이미지 관련 성능 병목과 보안 위험이 분리되어 정리되어 있다.
2. 이미지 URL 생성 반복이 큰 API가 식별되어 있다.
3. URL 분리, 검증 추가, 호출 수 감소 중 어떤 개선이 필요한지 판단할 수 있다.

## 4단계: 2차 API 및 동시성 측정

### 측정 대상

1. 마이페이지 리뷰 검색 API
2. 주문 목록 API
3. 추천 API
4. 주문 처리 API
5. 포인트 처리 API

### 확인할 내용

1. 검색 API에서 `LIKE '%...%'` 또는 정렬 비용이 큰지 확인한다.
2. 주문 목록 API에서 조인과 페이징 비용을 확인한다.
3. 추천 API에서 `DBMS_RANDOM` 사용 비용과 호출 빈도를 함께 본다.
4. 주문 처리 API는 동시 요청 기준으로 처리량과 실패 양상을 기록한다.
5. 포인트 처리 API는 `FOR UPDATE` 대기 시간을 기록한다.

### 종료 조건

1. 일반 조회 병목과 동시성 경합 병목이 구분되어 있다.
2. 주문과 포인트는 필요하면 별도 개선 트랙으로 분리할 수 있다.

## 5단계: 배치 작업 측정

### 측정 대상

1. 월간 베스트 리뷰 갱신 배치 수행 시간
2. 후보 리뷰 수 증가에 따른 실행 시간 변화
3. 배치 중 DB 부하
4. 배치 중 트랜잭션 유지 시간

### 종료 조건

1. 후보 리뷰 수와 배치 시간이 함께 기록되어 있다.
2. 배치 작업이 운영 API에 영향을 줄 가능성이 있는지 판단되어 있다.
3. 베스트 리뷰 쿼리 최적화 필요 여부가 수치로 결정되어 있다.

## 6단계: 병목별 개선 후보 정리

### 우선 검토할 패턴

1. 조인 비용이 큰 구간
2. 서브쿼리 비용이 큰 구간
3. `LIKE '%...%'` 검색
4. `OFFSET/FETCH` 페이징
5. `ROW_NUMBER` 기반 페이징 또는 정렬
6. `DBMS_RANDOM` 정렬
7. 이미지 URL 변환 반복
8. 페이징이 없는 목록 API
9. 주문 및 포인트 동시성 경합

### 개선 후보 분류

1. 즉시 개선 후보: 측정 결과 영향이 크고 수정 범위가 명확한 항목
2. 추가 검증 후보: 영향은 의심되지만 재측정이 필요한 항목
3. 보류 후보: 현재 수치상 병목이 아니거나 호출 빈도가 낮은 항목

### 종료 조건

1. 개선 후보가 영향도와 구현 난이도 기준으로 정렬되어 있다.
2. 보류 항목에는 보류 사유가 적혀 있다.
3. 선제 최적화가 아니라 측정 결과 기반으로 다음 작업이 정해져 있다.

## 7단계: 후순위 및 보류 항목 관리

### 후순위 항목

1. `ORDER BY DBMS_RANDOM.VALUE` 최적화
2. 베스트 리뷰 선정 쿼리 최적화
3. MyBatis cache 설정 검증
4. 목록 응답 DTO의 큰 텍스트 컬럼 정리

### 보류 기준

1. 실제 병목으로 확인되지 않은 API는 수정하지 않는다.
2. 운영 빈도가 낮은 관리자용 기능은 수치가 필요할 때만 다룬다.
3. 영향이 확인되지 않은 설정 변경은 적용하지 않는다.

## 진행 순서 요약

1. 측정 기준과 테스트 데이터를 먼저 고정한다.
2. 상품 목록, 검색, 리뷰, 이미지 발급 API를 먼저 측정한다.
3. 이미지 업로드와 URL 생성 경로를 점검한다.
4. 마이페이지, 주문, 추천, 포인트 API를 추가 측정한다.
5. 월간 베스트 리뷰 배치를 측정한다.
6. 병목으로 확인된 항목만 개선 후보로 정리한다.
7. 후순위 항목과 보류 항목을 별도로 관리한다.

# 트러블슈팅 Before/After 재현 검증 계획

기간: 2026-10-12 ~ 2026-10-16 (넥스트그라운드 지원 마감 10/16)

## 목표

이번 작업의 목표는 테스트를 많이 작성하는 것이 아니라, 이력서와 STAR 기법의 R(결과)에 쓸 수 있는 명확한 수치를 확보하는 것이다.

방법은 다음과 같다.

- 트러블슈팅의 수정 전 커밋과 수정 후 커밋을 각각 체크아웃한다.
- 두 커밋에 같은 테스트 코드를 적용해 실행한다.
- 테스트 결과를 수정 전/후로 비교해 수치로 기록한다.

수정 전/후 비교 테스트가 최우선 작업이다. 나머지 작업은 이 비교 결과를 정리하고 이력서에 반영하는 작업이다.

---

## 검증 대상

| 항목 | 수정 전 커밋 | 수정 후 커밋 | 비교 대상 메서드 |
|------|-------------|-------------|-----------------|
| 포인트 동시성 | `f82c1493` | `788998e3` | `PointService.addReviewPoint(int)`, `PointService.removeReviewPoint(int)` |
| Presigned URL 저장 오류 | `0884094a` | `63521f66` | `ProductReviewService.updateReview(int, int, String, double, List<String>)` |

두 항목 모두 수정 전/후 메서드 시그니처가 같아서 같은 테스트 코드를 양쪽에 그대로 적용할 수 있다.

`PointService.usePoint`는 수정 전 `usePoint(int)`, 수정 후 `usePoint(int, int)`로 시그니처가 달라 비교 대상에서 제외한다. 차감 시나리오는 시그니처가 같은 `removeReviewPoint`(리뷰 삭제 시 100P 회수)로 대신한다.

---

## 테스트 원칙

- 테스트 코드는 이 브랜치에서 한 벌만 작성하고, 수정 전/후 커밋에 같은 파일을 복사해 실행한다.
- 수정 전/후 커밋은 `git worktree`로 따로 띄운다. 과거 커밋 자체는 수정하거나 커밋하지 않는다.
- DB는 H2가 아니라 Testcontainers Oracle XE(`gvenzl/oracle-xe`)를 사용한다. `SELECT ... FOR UPDATE`의 락 동작이 H2와 다르기 때문이다.
- 동시성 테스트는 `ExecutorService`와 `CountDownLatch`로 요청을 동시에 출발시킨다.
- 동시성 테스트 메서드에는 `@Transactional`을 붙이지 않는다. 붙이면 모든 요청이 하나의 트랜잭션에 묶여 동시성이 재현되지 않는다.
- 결과가 예상과 다르면 그대로 기록하고, 이력서 문구를 결과에 맞게 정정한다.

## 측정 시나리오

### 포인트 동시성

변경 전 코드는 `UPDATE user_table SET point = point + #{amount}` 형태의 원자적 갱신이었다. 따라서 갱신 누락은 원래 발생하지 않았을 가능성이 높다. 실제로 고친 문제는 이력/잔액이 따로 커밋되는 것과 차감 시 잔액 검증이 없는 것이므로, 시나리오도 이 문제를 겨냥한다.

| ID | 시나리오 | 측정값 | 수정 전 예상 | 수정 후 예상 |
|----|---------|--------|-------------|-------------|
| P1 | 잔액 100P 사용자에게 `removeReviewPoint` 10건 동시 요청 | 최종 잔액, 성공/실패 건수, 이력 건수 | 잔액 음수(-900P) | 1건 성공, 잔액 0P |
| P2 | 잔액 0P 사용자에게 `addReviewPoint` 100건 동시 요청 | 최종 잔액(기대 10,000P), 이력 건수 | 일치 (원자적 갱신) | 일치 |
| P3 | 이력 INSERT 후 잔액 UPDATE에서 예외 주입 | 이력/잔액 불일치 건수 | 이력만 남음 | 둘 다 롤백 |
| P4 | P2 조건에서 요청별 처리 시간 | p50, p95, 전체 소요 시간 | 기준값 | 락 대기만큼 증가 |

P2와 P4는 수정 전에도 통과할 것으로 예상하지만 반드시 기록한다. "원래 원자적 갱신이라 누락은 없었고, 락 도입으로 대기 시간이 p95 __ms 늘었다"는 트레이드오프 설명의 근거가 된다.

### Presigned URL 저장 오류

변경 전 코드는 리뷰 수정 시 기존 이미지 매핑을 전부 삭제하고, 프론트가 보낸 값을 검증 없이 object key로 저장했다.

| ID | 시나리오 | 측정값 | 수정 전 예상 | 수정 후 예상 |
|----|---------|--------|-------------|-------------|
| S1 | 기존 이미지의 조회용 Presigned URL만 다시 보냄 | DB `image_url` 중 `http`로 시작하는 건수 | URL이 key로 저장됨 | 기존 key 유지 |
| S2 | 이미지 값 없이(null 또는 빈 리스트) 수정 | 수정 후 남은 이미지 수 | 기존 이미지 전부 삭제 | 기존 이미지 유지 |
| S3 | 새 object key만 보냄 (대조군) | 저장된 key | 교체 | 교체 |
| S4 | 기존 URL 1개 + 새 key 1개 혼합 | 수정 후 남은 이미지 수 (기대 2개) | URL과 key 모두 저장 | 새 key 1개만 남음 |

S4는 수정 후에도 기존 이미지가 사라질 것으로 예상한다. 이력서의 "남은 점(DTO를 신규 key와 기존 이미지 ID로 분리)"을 뒷받침하는 근거로 기록한다.

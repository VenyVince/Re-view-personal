# Refactor Review

작성일: 2026-05-05

## 점검 범위

- 백엔드: Spring Boot, Spring Security, MyBatis, MinIO, 설정 파일, 테스트 구성
- 프론트엔드: React, API 클라이언트, 라우팅/페이지 코드, 빌드 경고
- 확인 명령:
  - `.\mvnw.cmd test`: 성공, 테스트 1개 통과
  - `npm --prefix View run build`: 성공, ESLint 경고 다수 발생

## 리팩토링 및 수정 제안(및 우선순위 높은 순 정렬)

| 수정점 | 수정 원인 | 수정 결과 기대값 |
| --- | --- | --- |
| 인증 방식을 세션 기반 또는 토큰 기반 중 하나로 명확히 통일 | 프론트 `View/src/api/axiosClient.js`는 `localStorage`의 `token`을 `Authorization: Bearer`로 보내지만, 백엔드 `SecurityConfig`와 `UserController`는 세션/CSRF 중심으로 동작한다. 현재 구조는 인증 흐름을 오해하기 쉽고, 실제 토큰 검증 필터도 보이지 않는다. | 로그인, 권한 확인, 로그아웃, CSRF 처리 기준이 명확해지고 인증 관련 버그를 줄일 수 있다. |
| `SecurityConfig`의 `anyRequest().permitAll()` 정책 재검토 | 관리자와 마이페이지 일부 URL만 보호하고 나머지 API는 기본 허용 상태다. `reset-password`, 장바구니, 주문, 리뷰 액션처럼 사용자 식별이 필요한 API가 URL 패턴에서 빠지면 비인증 접근이 가능할 수 있다. | API별 인증/인가 요구사항이 명확해지고 비인가 요청 차단 범위가 넓어진다. |
| 인증 실패/인가 실패 응답 코드를 표준화 | `authenticationEntryPoint`와 `accessDeniedHandler`가 모두 400 계열 중 `400`을 반환한다. 인증 실패는 보통 `401`, 권한 부족은 `403`이므로 프론트에서 오류 원인을 구분하기 어렵다. | 프론트 오류 처리와 사용자 안내가 정확해지고, API 클라이언트/테스트에서 상태 코드 기준 검증이 쉬워진다. |
| `application.properties`의 민감 정보와 플레이스홀더 정리 | 메일 계정이 직접 노출되어 있고 `spring.mail.password=${your_app_password_here}` 형태의 잘못된 플레이스홀더가 있다. datasource username/password 앞 공백도 포함되어 있어 환경 변수 바인딩 혼선을 만들 수 있다. | 운영 환경 변수 관리가 안정화되고, 설정 누락/오타로 인한 런타임 장애 가능성이 줄어든다. |
| 테스트 프로파일의 MinIO 설정 키를 운영 코드와 일치 | `MinioProperties`는 `rootUser/rootPassword`를 사용하지만 `application-test.properties`에는 `minio.access-key`, `minio.secret-key`가 있다. 현재 컨텍스트 테스트는 통과하지만 실제 MinIO 클라이언트를 사용하는 테스트에서는 값이 비어 실패할 수 있다. | 테스트 환경과 운영 설정의 차이가 줄고, 이미지 업로드 관련 테스트를 추가해도 설정 오류를 먼저 밟지 않는다. |
| 개발/운영 Docker 및 환경 변수 문서 보강 | `infra/.env.example`, `Dockerfile`, `View/Dockerfile`이 있지만 백엔드/프론트/MinIO/DB 실행에 필요한 필수 환경 변수와 포트 계약이 코드 설정과 완전히 연결되어 보이지 않는다. | 신규 환경 구성 시간이 줄고, 배포 시 설정 누락으로 인한 장애를 줄일 수 있다. |
| 전역 예외 응답을 공통 JSON 포맷으로 변경 | `ExceptionHandlers`는 문자열 본문을 직접 반환하고, DB 예외는 `printStackTrace()`/`System.err`를 사용한다. 클라이언트가 오류 코드를 구조적으로 처리하기 어렵고 운영 로그 품질도 떨어진다. | `{code, message, timestamp, path}` 같은 일관된 응답으로 프론트 처리와 로깅/모니터링이 쉬워진다. |
| DTO 검증을 `jakarta.validation` 기반으로 추가 | 회원가입, 로그인, 주문, 리뷰 작성 등 주요 요청 DTO에 필수값/길이/형식 검증이 컨트롤러와 프론트에 흩어져 있다. 서버 단 검증이 약하면 잘못된 요청이 서비스/Mapper까지 내려간다. | 잘못된 입력을 API 경계에서 차단하고, 중복 검증 로직을 줄이며, 실패 응답도 일관화할 수 있다. |
| 백엔드 테스트를 컨텍스트 로드에서 기능 테스트로 확장 | 현재 백엔드 테스트는 `contextLoads()` 1개뿐이다. 인증, Mapper, 서비스 트랜잭션, 예외 응답, 주문/리뷰 핵심 플로우가 자동 검증되지 않는다. | 리팩토링 시 회귀를 빠르게 감지하고, API 계약 변경 여부를 테스트로 확인할 수 있다. |
| React Hook 의존성 경고 해결 | 프론트 빌드에서 `react-hooks/exhaustive-deps` 경고가 여러 파일에서 발생했다. 누락된 의존성은 오래된 상태를 참조하거나 예상치 못한 재렌더링 버그를 만들 수 있다. | 데이터 재조회, 필터 변경, 주문/상품 상세 화면의 상태 동기화가 안정화된다. |
| 사용하지 않는 변수/import 제거 | 프론트 빌드에서 `no-unused-vars` 경고가 다수 발생했다. 방치하면 실제 문제 경고가 묻히고 코드 가독성이 낮아진다. | 빌드 경고를 신호로 사용할 수 있고, 코드 리뷰 시 노이즈가 줄어든다. |
| 프론트 `alert()`와 `console.log()` 제거 또는 공통 알림/로깅으로 교체 | 빌드 전 검색 결과 다수의 `alert()`와 개발용 `console.log()`가 남아 있다. 사용자 경험이 페이지마다 다르고 운영 콘솔에 민감한 요청/응답 정보가 노출될 수 있다. | 토스트/모달 기반의 일관된 피드백을 제공하고, 운영 로그 노출 위험을 줄일 수 있다. |
| 프론트 테스트 전략 재정비 | CRA 기본 `App.test.js` 수준 외에 실제 페이지/훅/API 상태를 검증하는 테스트가 부족해 보인다. 빌드 경고는 통과하지만 사용자 플로우 안정성은 보장하지 않는다. | 로그인, 상품 조회, 주문, 마이페이지 같은 핵심 화면의 깨짐을 조기에 발견할 수 있다. |
| Spring Boot 진입점 패키지 정리 | `ReViewApplication`은 `org.spring.project.re_view` 패키지에 있고 실제 앱 코드는 `com.review.shop`에 있다. 현재는 `scanBasePackages`로 보정하지만 신규 개발자가 컴포넌트 스캔 범위를 놓치기 쉽다. | 패키지 구조가 직관적으로 바뀌고, 설정 의존도가 낮아져 신규 컴포넌트 등록 실수가 줄어든다. |
| MyBatis Mapper와 Java Mapper 네이밍/위치 규칙 정리 | XML 경로와 인터페이스 패키지가 기능별로 나뉘어 있지만 `Orders`, `userinfo/other`, `reportMapper.xml`처럼 대소문자와 명명 규칙이 섞여 있다. | Mapper 탐색성과 유지보수성이 좋아지고, 운영체제별 대소문자 이슈나 오타 가능성이 줄어든다. |
| 프론트 API 모듈 중복 정리 | `View/src/api/review/reviewApi.js`와 `View/src/api/reviews/reviewApi.js`처럼 유사한 API 폴더가 공존한다. 기능 추가 시 어느 모듈을 써야 하는지 혼란이 생길 수 있다. | API 호출 책임이 명확해지고, 응답 변환/오류 처리/엔드포인트 변경을 한 곳에서 관리할 수 있다. |
| 루트 `package.json`의 스크립트와 의존성 정리 | 루트와 `View`에 React 관련 의존성이 중복되어 있고, 루트 스크립트에 `"View": "npm --prefix view start"`처럼 대소문자가 맞지 않는 항목이 있다. | 설치 용량과 의존성 혼선을 줄이고, 로컬 실행 명령이 운영체제와 무관하게 안정화된다. |

## 우선순위 제안

1. 인증/인가 정책 정리: 보안 영향이 가장 크므로 `SecurityConfig`, 로그인 방식, 프론트 인증 저장 방식을 먼저 맞춘다.
2. 설정 파일 정리: 민감 정보, 환경 변수 플레이스홀더, MinIO 테스트 키 불일치를 수정한다.
3. 예외 응답과 DTO 검증 표준화: API 경계의 안정성을 높이고 프론트 오류 처리를 단순화한다.
4. 프론트 빌드 경고 제거: Hook 의존성, 미사용 코드, 개발 로그를 정리해 유지보수 신호를 깨끗하게 만든다.
5. 핵심 플로우 테스트 추가: 인증, 상품, 주문, 리뷰, 마이페이지 중심으로 회귀 테스트를 구축한다.

## 우선순위 정렬 근거

리팩토링 및 수정 제안 표는 장애 영향도와 선행 의존성을 기준으로 정렬했다. 먼저 인증/인가처럼 보안 영향이 크고 다른 API 동작의 전제가 되는 항목을 배치했고, 그 다음에는 실행 환경과 테스트 환경을 안정화하는 설정 항목을 두었다.

그 뒤에는 프론트와 백엔드가 함께 의존하는 API 응답/검증 표준화, 회귀를 막는 테스트, 실제 빌드에서 확인된 프론트 경고를 배치했다. 패키지 구조, Mapper 네이밍, API 모듈 중복, 루트 패키지 정리는 직접적인 장애 가능성은 상대적으로 낮지만 장기 유지보수 비용을 줄이는 작업이라 후순위로 두었다.

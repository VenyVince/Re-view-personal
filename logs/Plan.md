# Re_View 2주 안정화 계획

## 목표

Re_View는 기능을 크게 늘리는 쇼핑몰 프로젝트가 아니라, 취업용 포트폴리오로 정리 중인 프로젝트다.

현재 진행 상태:

- Day 1 완료: 로컬/Docker 실행 상태 확인
- Day 2 완료: Docker 환경 변수 관리 개선
- 다음 작업: Day 3 보안 정책 분류

앞으로 2주 동안의 목표는 다음과 같다.

- 로컬 및 Docker 실행 가능 상태 만들기
- Spring Security 세션 기반 인증/인가 정책 정리
- Docker 환경 변수 관리 개선
- 테스트 프로파일 안정화
- API 예외 응답과 DTO 검증 기준 정리
- 프론트 인증 요청 방식과 빌드 경고 정리
- 깨진 한글 문구와 Swagger 설명 정리
- 코드 수정과 검증 이후 README를 실제 구현 기준으로 수정

이 기간에는 JPA, JWT, AWS S3, Redis, Kafka, Elasticsearch 같은 큰 기술 전환이나 무거운 기술 스택을 도입하지 않는다.

## 1주차 - 실행 확인, Docker, 보안

### Day 1 - 현재 실행 상태 확인 - 완료

목표:

- 백엔드 로컬 실행 상태를 확인한다.
- 프론트엔드 로컬 실행 상태를 확인한다.
- Docker Compose 실행 상태를 확인한다.
- 큰 구조 변경 없이 현재 막히는 지점을 기록한다.

작업:

- Maven으로 백엔드 로컬 실행을 확인한다.
- `View` 폴더에서 프론트엔드 로컬 실행을 확인한다.
- `infra` 폴더에서 Docker Compose 실행을 확인한다.
- 누락된 환경 변수, DB 스키마 전제, MinIO bucket 전제, 실행 오류를 기록한다.

결과물:

- 실행 확인 메모
- 백엔드, 프론트엔드, Docker Compose, Oracle XE, MinIO에 필요한 환경 변수 목록
- 코드 문제와 로컬 환경/데이터 부족 문제의 구분

완료 기준:

- 백엔드 로컬, 프론트 로컬, Docker Compose 각각의 실행 가능 여부가 명확하다.
- 실패한 항목은 원인이 구체적으로 기록되어 있다.

### Day 2 - Docker 환경 변수 관리 개선 - 완료

목표:

- `.env` 파일이 Docker 이미지에 포함되지 않도록 한다.
- 필요한 환경 변수를 명확히 드러낸다.

작업:

- 백엔드 `Dockerfile`에서 `COPY infra/.env .env`를 제거한다.
- `infra/.env.example`을 추가하거나 갱신한다.
- Docker Compose는 계속 `env_file`로 런타임 환경 변수를 주입하도록 유지한다.
- Docker 이미지에 `.env`가 포함되지 않는 구조인지 확인한다.

결과물:

- `.env`를 복사하지 않는 백엔드 Dockerfile
- 민감 정보가 없는 `infra/.env.example`

완료 기준:

- Docker 이미지 빌드가 `infra/.env` 복사에 의존하지 않는다.
- 런타임 환경 변수는 Docker Compose를 통해 외부에서 주입된다.

### Day 3 - 보안 정책 분류

목표:

- 실제 API를 공개 API, 로그인 필요 API, 관리자 API로 분류한다.
- Spring Security 세션 인증 방식을 유지한다.

작업:

- 컨트롤러와 프론트엔드 API 호출을 함께 확인한다.
- `View/src/api/axiosClient.js`의 `Authorization: Bearer` 사용 여부를 확인하고 세션 인증 유지 기준과 충돌하는 부분을 기록한다.
- 엔드포인트를 다음 기준으로 분류한다.
  - 공개 API: 인증, 상품 목록/상세, 리뷰 목록/상세, 검색, Swagger
  - 로그인 필요 API: 장바구니, 위시리스트, 주문, 포인트, 주소, 결제수단, 마이페이지, 리뷰 작성/수정/삭제, 사용자 반응/신고성 API
  - 관리자 API: `/api/admin/**`
- 현재 `.anyRequest().permitAll()`로 노출된 API를 확인한다.

결과물:

- API 인증/인가 분류 메모
- `SecurityConfig` matcher 정책 초안
- 프론트 인증 요청 방식 정리 메모

완료 기준:

- 프론트엔드 사용 흐름을 확인하지 않은 API를 무리하게 막지 않는다.
- JWT는 도입하지 않는다.
- 세션 인증 유지 기준에서 제거하거나 유지해야 할 프론트 인증 코드가 구분되어 있다.

### Day 4 - SecurityConfig 인증/인가 적용

목표:

- Day 3에서 정리한 정책을 `SecurityConfig`에 반영한다.
- 변경 범위를 작고 설명 가능하게 유지한다.

작업:

- `SecurityConfig`의 request matcher를 수정한다.
- `/api/admin/**`는 관리자 권한으로 제한한다.
- 사용자 개인 데이터 관련 API는 로그인 필요 대상으로 제한한다.
- 상품/리뷰 공개 조회 API는 계속 접근 가능하게 유지한다.
- CORS와 CSRF 설정이 프론트엔드 로그인 흐름을 막지 않는지 확인한다.
- 프론트 공통 API 클라이언트에서 세션 인증과 맞지 않는 `Bearer token` 전송 코드를 제거하거나 후속 작업으로 명확히 기록한다.

결과물:

- 수정된 `SecurityConfig`
- 공개 API와 로그인 필요 API 구분 메모

완료 기준:

- 관리자 API는 관리자 권한이 필요하다.
- 사용자 개인 API는 더 이상 대부분 `permitAll()` 상태가 아니다.
- 상품/리뷰 공개 탐색 기능은 유지된다.
- 프론트 인증 요청 방식과 백엔드 인증 방식이 서로 충돌하지 않는다.

### Day 5 - 401/403 응답 상태 코드 정리

목표:

- 인증 실패와 권한 부족의 HTTP 상태 코드를 올바르게 정리한다.
- 큰 예외 응답 구조 개편은 `ErrorResponse` DTO 기준으로 작게 진행한다.

작업:

- 로그인하지 않은 사용자의 보호 API 접근은 401로 응답하도록 수정한다.
- 권한이 부족한 사용자의 접근은 403으로 응답하도록 수정한다.
- `ErrorResponse` DTO를 추가하고 전역 예외 응답을 공통 JSON 포맷으로 맞춘다.
- 회원가입, 로그인, 비밀번호 변경처럼 입력 오류가 잦은 요청 DTO부터 `jakarta.validation` 적용 범위를 결정한다.
- 응답 본문은 UTF-8로 유지한다.

결과물:

- 인증 실패와 권한 부족에 맞는 상태 코드
- 공통 예외 응답 포맷 초안 또는 적용 결과
- DTO 검증 적용 범위 메모

완료 기준:

- 미로그인 보호 API 접근은 401을 반환한다.
- 권한 없는 로그인 사용자는 403을 반환한다.
- 기존 로그아웃 동작은 유지된다.
- 프론트에서 오류 응답을 상태 코드와 JSON 본문 기준으로 구분할 수 있다.

## 2주차 - 테스트, 스케줄러, 인코딩, 검증

### Day 6 - 테스트 프로파일 안정화

목표:

- 테스트 프로파일 설정의 모순을 제거한다.
- `mvn test` 실패 원인을 해석 가능하게 만든다.

작업:

- `application-test.properties`에서 H2 URL과 Oracle driver가 섞인 문제를 수정한다.
- 기존 테스트가 Oracle 전용 스키마 없이 실행 가능하면 H2 기준으로 정리한다.
- 테스트 MinIO 프로퍼티 키를 운영 코드와 맞춘다.
  - `minio.url`
  - `minio.root-user`
  - `minio.root-password`
  - `minio.bucket`
- 테스트 프로파일의 깨진 한글 주석을 제거하거나 다시 쓴다.

결과물:

- 일관된 테스트 프로파일
- 첫 `mvn test` 실행 결과

완료 기준:

- 테스트 설정에서 H2 URL과 Oracle driver가 더 이상 섞이지 않는다.
- MinIO 프로퍼티 키가 `MinioProperties`와 일치한다.

### Day 7 - Maven 테스트 수정

목표:

- 백엔드 테스트를 가능한 범위까지 실행 가능하게 만든다.
- 컨텍스트 로드 1개에 머무르지 않고, 인증/예외/주요 서비스 중 최소 1개 이상을 기능 테스트 후보로 정리한다.
- 넓은 가짜 인프라나 과한 우회 코드를 만들지 않는다.

작업:

- `mvn test`를 실행한다.
- 좁은 설정 문제를 우선 수정한다.
- DB 스키마나 샘플 데이터가 없어서 실패한다면, 실패 원인을 숨기지 말고 기록한다.
- 설정 노이즈를 줄이는 데 필요한 최소 mock 또는 test property만 추가한다.
- 인증/인가, 예외 응답, 주문/리뷰 중 우선 테스트 대상을 정한다.

결과물:

- `mvn test` 통과 또는 남은 실패 원인 기록
- 백엔드 테스트 추가 후보 목록

완료 기준:

- 남은 테스트 실패가 있다면, 명백한 프로파일 설정 오류 때문은 아니다.
- 다음에 추가할 기능 테스트의 우선순위가 정리되어 있다.

### Day 9 - UTF-8 및 Swagger 문구 정리

목표:

- 깨진 한글 주석, Swagger 설명, 예외 메시지를 정리한다.
- 프론트 빌드 경고와 개발용 로그를 정리한다.
- 수정 범위를 필요한 문구로 제한한다.

작업:

- 깨진 한글과 실제 동작과 다른 API 설명을 검색한다.
- 깨졌거나 오해를 부르는 문구만 수정한다.
- 모든 수정은 UTF-8 기준으로 처리한다.
- 파일 전체 재저장은 피한다.
- `npm --prefix View run build`에서 나온 React Hook 의존성, 미사용 변수/import, `console.log` 경고를 우선순위별로 정리한다.

- 정리된 사용자 메시지, Swagger 설명, 주요 주석
- 프론트 빌드 경고 정리 결과
- 공통 알림/로깅 전환 후보 목록

완료 기준:

- 수정 대상 파일에 명백히 깨진 한글이 남아 있지 않다.
- Swagger 설명이 실제 없는 동작을 설명하지 않는다.
- 프론트 빌드 경고가 감소했거나, 남은 경고의 원인과 후속 처리 기준이 기록되어 있다.

## 2주 이후 계획

### CI

- 로컬 `mvn test`가 안정화된 뒤 GitHub Actions 테스트 워크플로를 추가한다.
- 현재 배포 워크플로는 self-hosted runner를 전제로 하므로 테스트 CI와 분리해서 검토한다.

### Redis Session

- 세션 인증 정책이 안정화된 뒤 Spring Session + Redis 도입을 검토한다.
- JWT로 전환하지 않는다.

### 추천 결과 캐싱

- 추천 SQL 성능 문제가 확인된 뒤 Redis Cache 적용 여부를 검토한다.

### MinIO 리버스 프록시와 도메인 정리

- `MINIO_URL` / `MINIO_PUBLIC_URL` 분리를 별도 작업으로 검토한다.
- `MINIO_URL`은 백엔드 컨테이너의 내부 접속 endpoint로 사용한다.
  - 로컬 Docker 예시: `http://minio:9000`
- `MINIO_PUBLIC_URL`은 클라이언트가 접근 가능한 공개 endpoint로 사용한다.
  - 로컬 Docker 예시: `http://localhost:9000`
  - 배포 예시: `http://서버IP:9000` 또는 이미지 도메인
- MinIO Client 역할 분리를 검토한다.
  - 내부 작업용 client: bucket 확인, 삭제, 검증, 리사이징, 바이러스 검사 등 서버 내부 작업
  - 공개 URL 발급용 client: presigned URL 발급
- 발급된 presigned URL의 host를 문자열 치환하지 않는다.
  - `minio:9000`을 `localhost:9000`으로 단순 변경하면 서명 불일치로 거절된다.
- public endpoint 기준 presigned URL 발급 구조를 검증한다.
- Docker Compose 환경에서 공개 endpoint는 브라우저와 백엔드 컨테이너가 모두 접근 가능한 주소인지 확인한다.
- 배포 환경에서 클라이언트가 접근할 이미지 공개 주소를 도메인 또는 리버스 프록시로 정리한다.
- 예시:
  - `https://images.example.com`
  - `https://api.example.com/minio`
- nginx 또는 인프라 프록시 설정으로 공개 주소를 MinIO에 연결한다.

### MinIO 내부 보강 작업

- presigned URL 발급 전에 bucket 존재 여부를 확인한다.
- 필요하면 bucket 자동 생성 또는 명확한 시작 실패 정책을 정한다.
- 업로드 파일 검증을 추가한다.
  - 허용 확장자
  - MIME type
  - 최대 파일 크기
  - 이미지 파일 여부
- 이미지 리사이징 또는 썸네일 생성 필요성을 검토한다.
- 바이러스 검사 또는 악성 파일 검사 도입 필요성을 검토한다.
- 사용되지 않는 object key 정리 정책을 검토한다.
- 이 작업은 현재 2주 안정화 범위에서는 제외하고, MinIO 구조 정리가 필요할 때 별도 브랜치에서 진행한다.

## 고정 제약

- MyBatis를 유지한다.
- Spring Security 세션 인증을 유지한다.
- MinIO Presigned URL 이미지 업로드 구조를 유지한다.
- Oracle XE를 주요 DB 대상으로 유지한다.
- AWS 기반 설정을 도입하지 않는다.
- JPA 또는 JWT를 도입하지 않는다.
- 변경은 작고 집중적으로 진행하며, 면접에서 설명 가능한 형태로 유지한다.

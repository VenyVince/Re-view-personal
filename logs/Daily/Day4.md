# Day 4 - SecurityConfig Authorization Apply

## 목표

Day 3에서 정리한 API 분류를 `SecurityConfig`에 반영한다. 변경 범위는 작게 유지하고, 상품/리뷰 공개 탐색 흐름은 깨지지 않게 검증한다.

## 작업 체크리스트

- [ ] Day 3의 API 분류 메모를 다시 확인한다.
- [ ] `SecurityConfig`의 request matcher 순서를 정리한다.
- [ ] Swagger/OpenAPI 문서 endpoint는 공개로 유지한다.
- [ ] 로그인/회원가입/아이디 찾기/임시 비밀번호 발급은 공개 여부를 확인한다.
- [ ] `/api/admin/**`는 `hasRole("ADMIN")`로 제한한다.
- [ ] 사용자 개인 데이터 API는 인증 필요로 제한한다.
- [ ] 상품/리뷰 공개 조회 API는 `permitAll()`로 유지한다.
- [ ] `anyRequest().permitAll()`을 유지할지, 더 보수적인 기본 정책으로 바꿀지 결정한다.
- [ ] CORS 설정이 프론트 origin을 허용하는지 확인한다.
- [ ] CSRF 설정이 세션 로그인 흐름과 충돌하지 않는지 확인한다.
- [ ] `View/src/api/axiosClient.js`에서 세션 인증과 맞지 않는 `Bearer token` 전송 코드를 제거하거나 후속 작업으로 명확히 기록한다.

## 검증 시나리오

- [ ] 공개 상품 목록 조회가 동작한다.
- [ ] 공개 리뷰 목록 조회가 동작한다.
- [ ] 미로그인 상태에서 보호 API 접근 시 거부된다.
- [ ] 일반 사용자로 관리자 API 접근 시 거부된다.
- [ ] 로그인 후 마이페이지 또는 장바구니 API 접근이 가능하다.
- [ ] 로그아웃 후 보호 API 접근이 다시 거부된다.

## 주의사항

- JWT 필터를 새로 추가하지 않는다.
- 세션 인증 유지가 기본 방향이다.
- 프론트 사용 흐름을 확인하지 않은 API를 무리하게 막지 않는다.
- matcher 순서는 구체적인 규칙을 먼저 두고, 넓은 규칙은 뒤에 둔다.

## 결과물

- 수정된 `SecurityConfig`
- 공개 API와 로그인 필요 API 구분 메모
- 프론트 인증 요청 방식 정리 결과

## 완료 기준

- 관리자 API는 관리자 권한이 필요하다.
- 사용자 개인 API는 대부분 `permitAll()` 상태가 아니다.
- 상품/리뷰 공개 탐색 기능은 유지된다.
- 프론트 인증 요청 방식과 백엔드 세션 인증 방식이 충돌하지 않는다.
